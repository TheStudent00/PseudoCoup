GNU C's operators, by the agreed classes of callee

Figure 1. GNU C's operators that clang lowers for all three of riscv64, x86-64 and aarch64: 1,115 of the 1,127. The other 12 are left out (Dee: "if anything didnt support an architecture, its not incuded"), and are listed below the chart (runs elv2_l77 to elv2_l79, log 377). Each operator is placed by a trace of clang 21.1.8's lowering code as it compiles one program for that operator for riscv64 (-std=gnu17, -O0): our clang, with that code compiled with the optimizer off and the full debug table on, run under gdb, which records every message the code sends LLVM and which of clang's functions sent it (runs elv2_l82 to elv2_l86, log 379). That clang writes the same IR as Ubuntu's for all 1,115 programs. Inner ring: the classes agreed in Dee's log 373, with changes 1, 2, 4, 5 and 7 of log 375. A callee is any callable object in the lowerer; its key is a message it sends LLVM itself. Simple: its own key, and no other calls. Hybrid: its own key and other calls, where no simple callee carries that key. Complex: only other calls; a key that a simple callee carries counts as a call to it. Undetermined: no key and no calls; a call to one is not counted. An operator's class is the class of the function clang picks for it (for a builtin, EmitBuiltinExpr on that builtin's path); its operands are its args. Second ring: how the trace placed each operator. Outer ring: each operator. Colour says one thing: the class.

What it does not show. A class per holder: each operator was traced with one program, so one set of holders (int + int here; p + i takes another path). The trace sees instructions, blocks put into a function and a phi's incoming values; it does not see globals or constants clang makes. Keys are compared by their full text, types included. Change 6 of log 375 (splitting keys) is not applied, so __builtin_ffs stays simple.
